Application de vérification des chauffeurs : recommandations techniques

Projet Allô Dabou / GNANGO · Document du 13/11/2026 · Portée : page de vérification (scan du QR par la police, la gendarmerie et les autorités), avec ses dépendances (enrôlement, base de données, badges).

Comment lire ce document. Chaque recommandation porte une priorité (P0 avant tout usage avec de vraies données, P1 avant le lancement, P2 après le lancement) et un niveau de preuve : SOURCÉ = appuyé par une source citée en fin de document (consultées le 13/11/2026, à revérifier avant déploiement car la documentation évolue) ; JUGEMENT = recommandation d'ingénierie de ma part, non démontrée par une source ci-dessous. 1. Synthèse

La version actuelle est un prototype fonctionnel : elle affiche le bon statut (vert, orange, rouge) pour un badge donné. Elle n'est pas prête pour de vraies données personnelles, car la protection repose sur le navigateur. Trois changements concentrent l'essentiel du gain de sécurité :

  1. Remplacer l'identifiant du QR (aujourd'hui ADB-0001, séquentiel) par un jeton aléatoire non devinable (§4.1).
  2. Fermer Firestore au navigateur et faire passer toute lecture par une Cloud Function qui vérifie qui appelle et ne renvoie que le strict nécessaire (§4.2 à 4.5).
  3. Calculer le statut sur le serveur, avec l'horloge du serveur (§4.6).

En parallèle, le traitement doit être mis en conformité avec la loi ivoirienne sur les données personnelles (§4.11), car l'application stocke identité, photo, téléphone et numéro de permis.

2. Diagnostic de la version actuelle

#ConstatRisqueReco.
D1Le QR contient le n° de badge séquentiel (ADB-0001, -0002…). Correction d'une affirmation antérieure : j'avais annoncé un identifiant aléatoire ; le code livré utilise le numéro d'affichage.Quiconque connaît le format peut tester 0001, 0002… et lire des fiches (énumération).§4.1
D2La page lit directement Firestore depuis le navigateur (drivers/{id}, agents/{code}).Les règles Firestore deviennent la seule barrière. Un code agent n'est qu'un nom de document : tout utilisateur connecté (même anonyme) qui connaît la structure peut lire la fiche complète.§4.2 à 4.4
D3Le code d'accès est vérifié côté navigateur, sans limite de tentatives, partagé par corps.Force brute possible ; pas de traçabilité par personne ; pas de révocation immédiate.§4.3, 4.4
D4Le statut (valide, provisoire, expiré) est calculé avec l'horloge du téléphone.Une heure de téléphone erronée ou modifiée fausse le résultat.§4.6
D5La même fiche (photo, téléphone, permis) est visible par tout porteur du lien si le jeu de règles est ouvert.Fuite de données personnelles.§4.5
D6Bibliothèques chargées depuis des CDN sans empreinte d'intégrité.Un CDN compromis exécuterait du code dans une page manipulant des données sensibles.§4.9
D7Aucune limitation de débit, aucun journal côté serveur fiable, aucune démarche de conformité.Abus non détectables ; risque juridique.§4.7, 4.8, 4.11

4. Recommandations détaillées

4.1 Jeton aléatoire dans le QR P0SOURCÉJUGEMENT

  • L'OWASP décrit l'IDOR : un attaquant accède à des objets en manipulant l'identifiant d'une URL, et recommande des identifiants complexes en défense en profondeur, mais précise que les contrôles d'accès restent indispensables, même avec des identifiants complexes[6]. L'OWASP déconseille aussi de « chiffrer » les identifiants[6].
  • Générer pour chaque badge un jeton de 16 octets aléatoires (22 caractères en base64url) avec un générateur cryptographique côté serveur. Le n° ADB-xxxx reste un numéro d'affichage, jamais utilisé pour interroger la base. JUGEMENT
  • Stocker uniquement l'empreinte SHA-256 du jeton en base (collection badgeTokens), de sorte qu'une fuite de base ne livre pas de QR utilisables. JUGEMENT
  • Placer le jeton dans le fragment de l'adresse (https://…/#t=JETON) : le fragment n'est pas envoyé au serveur d'hébergement, donc absent de ses journaux. La page le lit, appelle la fonction, puis l'efface avec history.replaceState. JUGEMENT
  • Perte ou vol du badge : révoquer le jeton (revoque: true) et en émettre un nouveau ; le QR imprimé ancien ne fonctionne plus. JUGEMENT
  • Saisie manuelle de secours (caméra refusée) : ne pas réutiliser le jeton de 22 caractères. Prévoir un code court (8 caractères en base32), réservé aux agents connectés, avec limitation de débit stricte (§4.7). Un numéro court peut s'énumérer ; le débit limité réduit ce risque sans l'annuler. JUGEMENT

4.2 Fermer Firestore au navigateur P0SOURCÉ

  • Les règles Firestore peuvent s'appuyer sur request.auth et sur des attributs personnalisés (auth.token) ; la documentation recommande de limiter l'accès en écriture au-delà de la simple condition « connecté »[2]. Une session anonyme est précisément une session « connectée » : elle ne prouve rien.
  • Règle proposée : tout refuser aux clients (extrait §6.1). Les Cloud Functions utilisent l'Admin SDK, qui contourne les règles : la documentation Firestore l'indique par une note citée dans une discussion technique (« The server client libraries bypass all Cloud Firestore Security Rules »)[12]. Source secondaire : à confirmer dans la documentation officielle.
  • Conséquence : la page de vérification et la page d'enrôlement ne doivent plus appeler db.collection(...) mais httpsCallable(...).

4.3 Authentification des agents P0SOURCÉJUGEMENT

  • Un code par personne (et non un code par corps) : traçabilité, révocation individuelle, expiration. JUGEMENT
  • Le code est échangé contre une session via la fonction agentLogin. Firebase prévoit ce schéma : un point d'accès serveur qui reçoit des identifiants et renvoie un jeton personnalisé (JWT signé), que le client utilise avec signInWithCustomToken() ; le jeton personnalisé peut porter des revendications supplémentaires, disponibles ensuite dans request.auth[4]. Ce jeton expire après une heure[4].
  • Stocker uniquement l'empreinte des codes (collection agentCodes), avec actif, expireLe, role, corps. Codes d'au moins 10 à 12 caractères aléatoires : un code court se devine. JUGEMENT
  • Révocation immédiate : verifyBadge relit agents/{uid}.actif à chaque appel (une lecture) ; désactiver un agent coupe son accès sans attendre l'expiration d'un jeton. JUGEMENT
  • Comptes administrateurs : vrais comptes Firebase Auth, avec la revendication role: "admin" posée uniquement depuis un environnement serveur privilégié avec l'Admin SDK (setCustomUserClaims) ; la charge utile des revendications ne doit pas dépasser 1000 octets ; les nouvelles revendications arrivent au client au prochain jeton émis[3]. Une authentification à deux facteurs pour les admins est à envisager : je n'ai pas vérifié sa disponibilité exacte dans votre configuration.

4.4 App Check sur les fonctions P1SOURCÉ

  • L'option enforceAppCheck: true d'une fonction appelable rejette les requêtes sans jeton App Check valide ; il faut firebase-functions ≥ 4.0.0 pour Node.js[1]. La documentation invite à comprendre l'effet sur les utilisateurs avant d'activer l'application stricte[1] : commencer en mode surveillance.
  • Protection contre le rejeu (bêta) : consumeAppCheckToken: true ; elle ne prend en charge que le SDK Node.js, ajoute un aller-retour réseau (donc de la latence) et n'est en général activée que sur les points sensibles[1]. Pour agentLogin et enrollDriver : oui ; pour verifyBadge : à décider selon la latence mesurée sur le réseau mobile local.
  • App Check réduit l'usage par des programmes étrangers à votre application ; il ne remplace ni l'authentification ni les contrôles d'accès. JUGEMENT

4.5 Réponses minimisées par rôle P0JUGEMENT

  • La fonction décide du contenu, jamais le navigateur (tableau §3). Le téléphone et le quartier ne sortent que pour un admin.
  • Le numéro de permis est masqué pour un agent (par exemple les 3 derniers caractères). À valider avec les autorités.
  • La photo et le prénom sont déjà visibles sur le badge physique ; les exposer au public n'ajoute pas d'information sensible et permet de détecter un faux badge (photo qui ne correspond pas au conducteur). Le jeton non devinable empêche la collecte en masse.
  • Pour un jeton inconnu ou révoqué : message neutre « Badge inconnu », sans distinguer les deux cas.

4.6 Statut calculé sur le serveur P0JUGEMENT

  • Remplacer le calcul dans le navigateur (horloge du téléphone) par un calcul dans verifyBadge avec l'heure du serveur. La page ne fait qu'afficher statut.code et statut.couleur.
  • Règle métier à figer par écrit : badge provisoire = émission + 3 mois ; passage à « Permis » uniquement après saisie d'un numéro et d'une fin de validité de permis par un admin ; suspension prioritaire sur tout autre état.
  • Définir le fuseau et la règle de fin de journée (le badge est-il valable jusqu'à 23 h 59 le dernier jour ?) pour éviter les litiges lors d'un contrôle.

4.7 Limitation de débit et détection d'abus P1JUGEMENT

  • Compteurs par agent et par adresse IP (échecs de connexion, jetons inconnus), avec blocage temporaire au-delà d'un seuil. Seuils à fixer après quelques semaines de données réelles.
  • Journaliser aussi les tentatives sur jeton inconnu : c'est le signal d'une énumération.
  • Je ne peux pas confirmer qu'un mécanisme natif de Firebase suffise pour la limitation de débit des fonctions appelables ; le plus sûr est un compteur à vous dans Firestore (transaction) ou un service dédié, à étudier.

4.8 Journal d'audit P1JUGEMENT

  • Pour chaque contrôle : date serveur, agentId, rôle, identifiant interne du chauffeur, statut renvoyé. Écrit uniquement par la fonction.
  • Ne pas enregistrer la position GPS de l'agent sans base légale et information préalable (voir §4.11).
  • Fixer une durée de conservation du journal et une procédure de consultation (qui peut le lire, sur demande de qui). La durée est une décision juridique : voir §8.

4.9 Front : HTTPS, caméra, en-têtes, bibliothèques P1SOURCÉJUGEMENT

  • HTTPS obligatoire pour le scan. getUserMedia() n'est disponible que dans un contexte sécurisé (HTTPS, ou localhost, ou file:///) ; en contexte non sécurisé, navigator.mediaDevices est indéfini et la caméra est inaccessible ; l'autorisation de l'utilisateur est toujours demandée[5]. Un hébergement sans HTTPS rend donc le scan impossible.
  • Politique d'autorisations. L'en-tête Permissions-Policy: camera=(self) limite la caméra à votre propre origine[5].
  • Autres en-têtes (extrait §6.4) : HSTS, X-Content-Type-Options, Referrer-Policy: no-referrer, frame-ancestors 'none' contre l'habillage dans une autre page, et une politique CSP stricte. JUGEMENT
  • Bibliothèques (Firebase, jsQR, qrcode-generator) : les héberger vous-même avec versions figées, ou ajouter une empreinte d'intégrité (integrity) si elles restent sur un CDN. Réduit le risque D6. JUGEMENT
  • Session agent : conserver la session en mémoire ou sessionStorage, déconnexion automatique après une période d'inactivité (par exemple 15 minutes, à ajuster), bouton de déconnexion visible, car un téléphone peut être prêté ou perdu.
  • Affichage : statut en grand, couleur et texte (ne pas se reposer sur la couleur seule, utile en plein soleil et pour le daltonisme), contraste élevé, boutons larges.

4.10 Réseau, hors ligne et scanner P2JUGEMENT

  • PWA avec service worker qui met en cache la coquille de l'application (HTML, CSS, JS), mais jamais les réponses contenant des données personnelles. Hors ligne : afficher clairement « Pas de connexion : contrôle impossible » plutôt qu'un ancien résultat.
  • Option avancée à étudier : QR contenant une charge signée (signature à clé publique) vérifiable hors ligne pour l'authenticité du badge. Limite : elle ne montre ni suspension ni révocation survenues après l'émission. À n'envisager que si la couverture réseau des postes de contrôle pose problème.
  • Scanner : la page utilise la bibliothèque jsQR. Je ne peux pas confirmer la disponibilité de l'API native BarcodeDetector sur les téléphones visés ; garder jsQR en solution de repli et tester sur des téléphones Android d'entrée de gamme, en plein soleil, avec des cartes plastifiées (reflets).
  • Taille et correction d'erreur du QR : conserver au moins 19 mm de côté et le niveau de correction d'erreur « M » ; un tampon ou une rayure sur le badge ne doit pas empêcher la lecture. À valider par tests d'impression réels.

4.11 Conformité : données personnelles en Côte d'Ivoire P0SOURCÉ

  • Le cadre est la loi n° 2013-450 du 19 juin 2013 relative à la protection des données à caractère personnel[9], dont l'autorité de protection est l'ARTCI[11].
  • L'ARTCI a rappelé que tout traitement de données à caractère personnel doit faire l'objet d'une déclaration préalable ou d'une autorisation[7]. Un article de presse reprend l'article 5 de la loi : le traitement est soumis à une déclaration préalable[8].
  • La loi et l'ARTCI font intervenir un « Correspondant à la protection des données » (articles 42 et 45 cités par l'ARTCI)[10].
  • À prévoir : finalités écrites (identification et contrôle des chauffeurs de moto-taxi), liste des données collectées, durée de conservation, information et consentement ou autre base légale au moment de l'enrôlement, droits des personnes (accès, rectification…), cadre écrit de l'accès par la police et la gendarmerie (protocole ou convention). L'ARTCI rappelle aux jeunes que la loi leur reconnaît des droits sur leurs données[13].
  • Les points exacts (déclaration ou autorisation, statut de la photo, durée de conservation, base légale de l'accès des forces de l'ordre) sont en section 8 : je ne peux pas les confirmer. À valider avec l'ARTCI ou un conseil juridique avant d'enrôler de vrais chauffeurs.

4.12 Exploitation P1JUGEMENT

  • Environnements séparés : un projet Firebase de test (avec données fictives) et un projet de production.
  • Alertes sur les pics d'erreurs et de jetons inconnus ; sauvegardes planifiées de la base (méthode et fréquence à définir : je ne l'ai pas vérifié ici).
  • Rotation et révocation : procédure écrite pour désactiver un agent, un admin ou un lot de badges.
  • Aucun secret (clé de service) dans les pages HTML ni dans un dépôt public. La configuration Firebase côté navigateur n'est pas un secret, mais elle n'est protégée que par vos règles et App Check.

6.2 Fonction verifyBadge (Node.js, 2e génération)

const { onCall, HttpsError } = require("firebase-functions/v2/https");
const { initializeApp } = require("firebase-admin/app");
const { getFirestore, FieldValue } = require("firebase-admin/firestore");
const crypto = require("crypto");

initializeApp();
const db = getFirestore();
const sha256 = (s) => crypto.createHash("sha256").update(s).digest("hex");
const masque = (n) => (n ? "***" + String(n).slice(-3) : "");

function statut(d, now) {
  if (d.suspendu) return { code: "SUSPENDU", couleur: "rouge" };
  const fin = d.dateExpiration ? new Date(d.dateExpiration) : null;
  if (!fin || isNaN(fin)) return { code: "INCONNU", couleur: "gris" };
  if (fin < now) return { code: "EXPIRE", couleur: "rouge" };
  return d.typeBadge === "permis"
    ? { code: "VALIDE", couleur: "vert" }
    : { code: "PROVISOIRE", couleur: "orange",
        joursRestants: Math.ceil((fin - now) / 86400000) };
}

exports.verifyBadge = onCall(
  { enforceAppCheck: true, region: "europe-west1", timeoutSeconds: 10 },
  async (request) => {
    const token = String(request.data?.token ?? "");
    if (!/^[A-Za-z0-9_-]{22,64}$/.test(token))
      throw new HttpsError("invalid-argument", "Jeton invalide.");

    // 1) Rôle de l'appelant ("public" par défaut)
    let role = "public", agentId = null;
    const r = request.auth?.token?.role;
    if (r === "agent" || r === "admin") {
      const a = await db.collection("agents").doc(request.auth.uid).get();
      if (a.exists && a.data().actif === true) { role = r; agentId = request.auth.uid; }
    }

    // 2) TODO : limitation de débit par agentId / adresse IP

    // 3) Recherche par empreinte du jeton
    const t = await db.collection("badgeTokens").doc(sha256(token)).get();
    if (!t.exists || t.data().revoque) {
      await db.collection("controles").add({
        date: FieldValue.serverTimestamp(), role, agentId, driverId: null, statut: "JETON_INCONNU" });
      return { statut: { code: "INCONNU", couleur: "gris" } };
    }
    const snap = await db.collection("drivers").doc(t.data().driverId).get();
    if (!snap.exists) return { statut: { code: "INCONNU", couleur: "gris" } };
    const d = snap.data();
    const st = statut(d, new Date());           // heure du serveur

    // 4) Journal d'audit
    await db.collection("controles").add({
      date: FieldValue.serverTimestamp(), role, agentId, driverId: snap.id, statut: st.code });

    // 5) Réponse minimisée selon le rôle
    const base = { statut: st, prenoms: d.prenoms, photo: d.photoURL, badge: d.badgeNumero };
    if (role === "public") return base;
    const agent = { ...base, nom: d.nom, type: d.typeBadge, fin: d.dateExpiration,
                    plaque: d.plaqueMoto, permis: masque(d.permisNumero) };
    if (role === "agent") return agent;
    return { ...agent, telephone: d.telephone, quartier: d.quartier };
  }
);

6.3 Fonction agentLogin et revendications admin

const { getAuth } = require("firebase-admin/auth");

exports.agentLogin = onCall(
  { enforceAppCheck: true, consumeAppCheckToken: true, region: "europe-west1" },
  async (request) => {
    const code = String(request.data?.code ?? "").trim();
    if (code.length < 10) throw new HttpsError("invalid-argument", "Code invalide.");
    // TODO : compter les échecs par IP et bloquer temporairement

    const snap = await db.collection("agentCodes").doc(sha256(code)).get();
    const c = snap.exists ? snap.data() : null;
    const expire = c?.expireLe?.toDate?.();
    if (!c || c.actif !== true || (expire && expire < new Date()))
      throw new HttpsError("permission-denied", "Code invalide ou désactivé.");

    const customToken = await getAuth().createCustomToken(c.agentId,
      { role: c.role, corps: c.corps });
    return { customToken };            // le client appelle signInWithCustomToken()
  }
);

7.1 Tests de sécurité (phase 1)

  1. Depuis la console du navigateur avec le SDK client, tenter de lire drivers, agents, agentCodes : tout doit être refusé.
  2. Appeler verifyBadge avec des jetons aléatoires en boucle : refus après un seuil, entrées « JETON_INCONNU » dans le journal.
  3. Appeler les fonctions sans jeton App Check (script externe) : rejet.
  4. Désactiver un agent : son prochain contrôle est refusé immédiatement.
  5. Modifier l'heure du téléphone : le statut affiché ne change pas.
  6. Badge suspendu, expiré, provisoire à J-1, provisoire à J+1, permis expiré : statuts attendus.
  7. Révoquer un jeton : l'ancien QR affiche « Badge inconnu » ; le nouveau fonctionne.
  8. Vérifier que la réponse « public » ne contient ni nom de famille, ni téléphone, ni quartier, ni plaque, ni permis (examiner la réponse réseau brute).

7.2 Tests de terrain (phase 2)

  1. Lecture du QR sur 3 à 5 modèles de téléphones Android d'entrée de gamme, en plein soleil, de nuit, avec carte plastifiée neuve et usée.
  2. Réseau mobile faible ou coupé : message clair, pas de résultat périmé.
  3. Caméra refusée par l'agent : le chemin de secours (code court) fonctionne et reste limité en débit.
  4. Temps entre le scan et l'affichage du statut sur le réseau local réel (à mesurer, aucun objectif chiffré n'est garanti ici).
  5. Perte d'un téléphone d'agent : procédure de désactivation exécutée de bout en bout.

8. Ce que je ne peux pas confirmer

  • Juridique. Je ne peux pas confirmer si votre traitement relève d'une simple déclaration ou d'une autorisation préalable de l'ARTCI : les sources trouvées parlent de « déclaration préalable ou autorisation »[7] sans trancher pour ce cas.
  • Je ne peux pas confirmer la base légale qui permettrait à la police et à la gendarmerie d'accéder à ces données, ni les formalités éventuelles (texte réglementaire, convention).
  • Je ne peux pas confirmer si la photo d'identité relève des données biométriques au sens de la loi. L'ARTCI a publié un communiqué sur l'usage de la biométrie pour le contrôle[14], dont je n'ai lu qu'un extrait.
  • Je n'ai pas relu intégralement le texte de la loi[9] ; je ne peux donc pas citer les durées de conservation, les sanctions précises ni le contenu exact des articles 42, 45 et 51 hors des extraits des sources citées.
  • Technique. Disponibilité de l'API BarcodeDetector sur les téléphones ciblés ; liste complète des domaines à autoriser dans la CSP avec App Check ; existence d'un mécanisme natif de limitation de débit pour les fonctions appelables ; durée de vie de la session Firebase obtenue après signInWithCustomToken (le jeton personnalisé expire après une heure[4], mais je n'ai pas vérifié le comportement de renouvellement de la session ensuite : à tester) ; méthode et fréquence des sauvegardes.
  • Le contournement des règles Firestore par l'Admin SDK s'appuie sur une source secondaire[12].
  • Aucun extrait de code de ce document n'a été exécuté. Aucune mesure de performance n'a été faite.
